# DIAG-flat-speed: why the flat T fails at some design speeds (FX1, D185 part 1)

Rig: Release at 223242737c plus scratch env hooks (not committed), scratch Catch2 test, flat T map `ConstructJunctionTMap(spec, nullptr, nullopt, false)`. Spec = `MakeJunctionSpec(RAILTYPE_RAIL, 1, 1, 4, train=14194,1090000,561,25,<speed>)` with unlimited rail, year 2000, no inflation, realistic acceleration, sd 4. It reproduces B0b exactly: rail_piece 75, bridge(1) 804; builds at 100/120/180, fails at 140/160/196.

## Q1. Per height (g = ml_gap = 1, so the loop runs heights 11..14)
- Curve spacing (`DeriveCurveSpacing`, src/junction_generator.cpp:88, used at :1171) by speed: 100:2, 120:3, 140:4, 160:5, 180:6, 196:7 (tl 4, cap 2*tl = 8).
- 160 km/h (prio 14; NOTE `SizeJunctionPrio` returns NoLayout here, error 3, because the sweep `GenerateJunctionUnchecked` fails at 140 and 160, so `junction_export` without `prio=` never reaches the T map; B0b used prio=14): h11 A->S failed (no route in 11 rows at spacing 5; spacing <= 3 routes at h11). h12 "no valid skeleton": crossing set on lane A is x 27..49 (A->S crosses the W row at 27.., N->A at 49), conflict cycle HeadClear + EqualLength + Span (junction_skeleton.cpp:133-): the bridge must span zmax-zmin+2*k_head <= nmax+1 = 11, here 22 wide. h13, h14: skeleton fine (crossing x 38..39, x_ls 42) but B->S failed (junction_generator.cpp:1664, router finds no route to the S stub given A->S, N->A and the lane bridges already laid).
- 196 km/h (prio 15, the brief's log): h11 A->S; h12, h13 N->A; h14 no valid skeleton (zone 23..52 on lane A).
- The loop stops at 14 because `height_limit = g + 13` for terrain == nullptr (junction_generator.cpp:1096, D170a "the flat cap"); with a terrain it is the snapshot's rows. There is no proof behind 13; `growth_cannot_help` runs for the line router only.

## Q2. Both a bound and a cost effect; no rule forbids the flat layout
- Bound (evidence): raising the cap alone builds 140 at h15, 160 at h17, 196 at h16 with the real prices.
- Cost effect (evidence): same spacing, same prio, only prices changed. Spacing 5: test-spec prices (100, 500+200n) h13; real prices h17; rail 150 with real bridges h13; rail 1000 h11. Spacing 4: real h15, rail 1000 h11. Prio 10..16 changes nothing. Scale does not matter (inflation x1..x4 gives the same pattern); the bridge:rail ratio does. The old router picks each edge by cost alone, so a cheap-rail spec takes long rail detours that block B->S.
- With the cap raised to g+60 and real prices, spacing 8 (speed ~210+, tl 4) never builds: from h20 "B->S has no start" at every height (a price effect too: rail 1000 builds it at h17).
- With cheap bridges (bridge(n) = 0.1*rail*(n+2), rail 1000) and no cap, every spacing builds for g 1..3, tl 2..12, except g=1 with spacing >= 10 (tl >= 5, speeds far above 200 km/h) and g=2 spacing 12: no layout up to g+45. First heights, relative to g: spacing <= 3: 10; 4: 10; 5: 12; 6: 13; 7: 15 (tl 4) to 22 (tl 12); 8: 16..23.

## Q3. Smallest fix (scratch-tested, not committed)
1. Route the flat gate with canonical prices: rail_piece 1000, bridge(n) = 100*(n+2) (junction_generator.cpp ~:864, before `MakeJunctionFrame`, when terrain == nullptr && !line_router). Reason: the gate only needs ports, hub and first height; a bridge passes the curve-spacing and crossing rules that cost-led detours break.
2. Cap for the flat gate `height_limit = g + 14 + tl` (:1096). Measured: sufficient for every buildable cell of the grid above (tightest: g 3, tl 12, spacing 12 needs g+26 = 14+12; g 1, tl 12, spacing 9 needs g+23). It is an envelope of measurements, not a proof; the proof would bound the crossing set's width (the HeadClear/Span cycle above).
3. Apply it at the gate only (junction_game.cpp:424, junction_generator.cpp:881, junction_gui.cpp:676), as its own function. Applied inside `ConstructJunctionTMap` for all flat calls it breaks two tests: "the constructed T is rule-clean" (rule 3, curve speed 111 below 160 at tile 1,3: the old router has no curve state across edges) and "the line-router T starts at the flat height" (layout identity with the line router, junction_map.cpp:67, :266). The gate's layout is used only for height, hub and ports (junction_generator.cpp:912-915), so unclean is acceptable there.
- Cost, flat build ms (Release, prio 14, noisy +-20%): before 100: 4.2 ok, 140: 14.1 fail, 160: 14.6 fail, 196: 19.7 fail; after 100: 3.6, 140: 11.7 (h11), 160: 17.5 (h13), 196: 26.2 (h16), 180: 31.4 -> 28.1. Computed once per spec (P3), far below the 100 ms hover target.
- Not verified: that the line router at real prices then builds on flat terrain from this first height (its box is the snapshot, margin 4); and `SizeJunctionPrio` still fails at 140/160 (sweep), a separate defect that also blocks the GUI slider.
