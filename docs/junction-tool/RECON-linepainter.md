# RECON: line painter (D112)

Read-only recon on branch feature/junction-tool. Line numbers are from the tree at commit 46e41dc3e5.

## A. OpenTTD's rail drag, end to end

Toolbar button to tool:
- `HandlePlacePushButton(this, widget, cursor, style)` (`rail_gui.cpp:650`) sets the cursor and place mode. Per-widget cursor is `GetCursorForWidget` (`rail_gui.cpp:~600`) and per-widget style is `GetHighLightStyleForWidget` (`rail_gui.cpp:618-634`). The four autorail buttons use `HT_LINE | HT_DIR_*` (`:618-621`). The junction button uses `HT_RECT` (`:631`).
- Click: `OnPlaceObject(pt, tile)` (`rail_gui.cpp:694`) calls `VpStartPlaceSizing(tile, method, DDSP_PLACE_RAIL)` for the rail tools (junction branch at `:749`). `VpStartPlaceSizing` is at `viewport.cpp:2844`. It stores `selstart`, switches `_special_mouse_mode` to `Sizing`, and turns the place mode into `HT_SPECIAL` while keeping the drawstyle (`:2867-2873`).
- Drag: each mouse move calls `OnPlaceDrag(select_method, proc, pt)` (`rail_gui.cpp:757`), which calls `VpSelectTilesWithMethod(x, y, method)` (`viewport.cpp:3348`). With `VPM_RAILDIRS` or `VPM_SIGNALDIRS` set, it stores `selend` and calls `CalcRaildirsDrawstyle` (`viewport.cpp:3127`). That function snaps the line from selstart to the cursor to one of the 6 track directions (X, Y, HU, HL, VL, VR) and writes the result into `_thd.next_drawstyle` as `HT_LINE | HT_DIR_*`. A long autorail drag is therefore always ONE straight run, either axis or diagonal, with a 2x1 variant.
- Draw: `DrawAutorailSelection(ti, style)` (`viewport.cpp:1005`) is called per tile from the highlight code (`viewport.cpp:~1195-1208`). It draws a track-sprite overlay on every tile of the current line. The overlay is the engine's own, not a ghost store.
- Release: `OnPlaceMouseUp(select_method, select_proc, pt, start_tile, end_tile)` (`rail_gui.cpp:770`). `DDSP_PLACE_RAIL` goes to `HandleAutodirPlacement` (`:402`). If the drawstyle has `HT_RAIL` (one tile), it calls `GenericPlaceRail` (`:105`). Otherwise it calls `DoRailroadTrack(track)` (`:391`), which posts `Commands::BuildRailLong` with (end, start, railtype, track, auto_remove_signals, false).
- Command: `CmdBuildRailroadTrack(flags, end_tile, start_tile, railtype, track, auto_remove_signals, fail_on_obstacle)` (`rail_cmd.cpp:942`) calls `CmdRailTrackHelper` (`:885`). `ValidateAutoDrag` (`:826`) checks that start, end and track agree. The helper then loops `BuildRail` per tile, advances by `_trackdelta[trackdir]`, and toggles the half-tile bit for non-diagonal tracks (`:919-922`). Obstacles are skipped unless `fail_on_obstacle` is set. There is no curve or route notion: one straight line, one railtype, one command. The cost comes from the same command in test mode.
- Signals: `HandleAutoSignalPlacement` (`rail_gui.cpp`) posts `BuildSignalTrack` (`CmdSignalTrackHelper`, `rail_cmd.cpp:1277`). It uses the D97 density walk and has the same one-straight-run limit.

Reusable hooks for a new drag tool:
1. `VpStartPlaceSizing` / `OnPlaceDrag` / `OnPlaceMouseUp` give the press, drag and release events. They also give auto-scroll and the sizing mouse mode. `DDSP_*` is an enum in `viewport_type.h`, so a new `DDSP_BUILD_LINE` is needed.
2. The `_thd.selstart/selend` and `pt.x == -1` abort convention.
3. `HT_SPECIAL` plus a ghost store (the junction approach) when the line is not a straight run. The engine's `HT_LINE` highlight cannot draw a curve, so the painter must NOT rely on it. Use `HT_RECT` with `SetTileSelectSize(1,1)` as the junction tool does (`junction_gui.cpp:~520`), so only the cursor tile shows the selection box.
4. The viewport already draws a ghost store per tile (`viewport.cpp:1346-1348`, `DrawJunctionGhost`, `DrawJunctionGhostOutline`).
5. Straight stretches may still be built with `BuildRailLong` per track, one command per straight run. That is cheap and tested, but the junction path posts per-piece steps, which is simpler to unify.

Caveat: dragging with `VpStartPlaceSizing` starts on press. The junction tool is click-only (`OnPlaceObject` leads to `JunctionToolClick`). A painter needs `OnPlaceObject` to start sizing, and `OnPlaceDrag` to run the router on the cursor tile (debounced). Release then calls `OnPlaceMouseUp` to build.

## B. How the junction tool plugs into the rail toolbar

- Widget `WID_RAT_BUILD_JUNCTION`: button at `rail_gui.cpp:968`, hotkey `:926`, cursor `:605`, style `HT_RECT` `:631`. Pressing it calls `ShowBuildJunctionWindow(this, _cur_railtype)` (`:678-679`). Click on the map goes to `JunctionToolClick(tile)` (`:749-750`, `junction_gui.cpp:1035`), which calls `BuildJunctionWindow::StartBuild`. Abort handling is at `rail_gui.cpp:832-845`. `RestoreJunctionPlacement` (`:2161`) re-arms the cursor after a sub-pick.
- Window: `BuildJunctionWindow` in `junction_gui.cpp` (about 1000 lines). It holds the notation fields (ml_gap, branch_gap, tl and so on), cache, a worker job (`library_job`) and hover logic (`hover_tile`, `ShowHover` `:459`, `ShowResult` `:490`). The painter needs its own notation field and a start-picking state, not this window's junction-specific settings. It could be a second panel in the same window or a new `BuildLinePainter` window with the same lifecycle.
- Ghost store `JunctionGhost` (`junction_gui.h:48-56`, `junction_gui.cpp:89-190`):
  - `Set(layout, origin, height, railtype, bridge_types, estimate)`. Per-tile `JunctionGhostTile` holds `tracks`, `signals`, `head`, `span` and `bad`.
  - `SetPinned` / `IsInPinnedFootprint` keep the ghost on screen while a build runs.
  - Drawing goes through `DrawJunctionGhost` and `DrawJunctionGhostOutline` (`junction_ghost_draw.h` has the track, signal and bridge sprite helpers).
  - Painter reuse: it takes a `JunctionLayout` plus an origin tile, so a line converted to a layout (tracks, bridges, signals) drops straight in. The layout is in canonical offsets from an origin, so the painter picks the origin as the start tile and uses offsets in map axes (rotation 0, no mirror), or applies `ApplyJunctionOrientation`.
- Cost: `EstimateJunction(layout, origin, pricing)` (`junction_layout.h:128`) and `ShowEstimatedCostOrIncome`, as in `ShowResult`. `GameJunctionPricing` queries real clear cost and slopes.
- Sequencer (`junction_build.h`): `MakeJunctionBuildSteps(layout, origin)` returns the steps (rail, bridge, signal) in build order. `JunctionSequencer` posts one at a time from `OnRealtimeTick`, with Retry and Cancel. `GameJunctionStepPoster` is the real poster, and a fake poster is available for tests. Directly reusable, because any `JunctionLayout` builds the same way.
- Directly reusable by the painter: the ghost store and drawing, the estimate, step maker, sequencer and poster, `BridgeType` choice (`bridge_types`), the signal pass (`junction_signal_pass.cpp`, D97 walk) when given a layout, and `ParseJunctionNotation` (`junction_generator.h:26`, returns a `gap` and an error).
- Not reusable as is: the generator and library fit (`FitJunctionLibraryNear`) and the `MakeJunctionFrame` assumptions.

## C. The router: how far from a line state

Current `FindJunctionRoute` (`junction_router.cpp:440`, `Router::Run` `:378`):
- A* with state `RouterNode {x, y, trackdir, u, hand, prev_gap_ok, pair, first, on_bridge}` packed into 50 bits (`:47`). The state is ONE track's last piece. Successors are F, L, R plus B<n> bridges (`Successors` `:288`).
- Curve grammar is the `u / hand / prev_gap_ok / pair` machinery in `TurnAllowed` (`:220`) and `MakePiece` (`:240`). `u` is in half-units (axis 2, diagonal 1), capped at `max(curve_spacing, s_bend_window)`.
- Costs: `rail_piece + TerrainCost + crossable_cost + turn_cost`, bridge cost via `prices.bridge(n)`. Heuristic is Manhattan to the nearest goal times `rail_piece` (`:281`).
- Rules: a piece must be in `request` bounds, off bridge heads, and satisfy `terrain->UsableAt(x, y, plane)` (`:268`). Bridge spans are checked against `SpanOk` (`:330ish`). Track clash is `ConflictsAt` (`:195`). The only allowed share of a tile is a parallel pair (Upper/Lower, Left/Right).
- Output is a `JunctionRoute {start, start_trackdir, moves string}`, rasterized by `RasterizeJunctionRoute` (`junction_route.h`) into pieces and bridges and merged by `AddRasterToLayout`. It is a single track with an exact goal Trackdir list (goal-pieces, not a point), with a single fixed `plane` (one height).
- The router has no cursor-as-goal concept (goals are exact `JunctionRouteEnd` pieces) and no step cap besides `max_expansions` (200000). For a drag, the goal is "get as close as possible to the cursor heading toward it", so a new termination rule is needed: best-so-far by distance, or goals as the set of pieces at the cursor tile.

Option A (route the centreline, derive offset tracks):
- Pro: reuses `FindJunctionRoute` unchanged; cheap.
- Corner fix-up problem in plain words: a track offset sideways from a curving centreline does not follow the same tiles. On a straight run the offset track is just one or more tiles over, parallel. At a 45-degree turn, the inner track turns sooner and the outer one later, and on this tile grid a track can only run on axis or diagonal pieces, so the two tracks' diagonal runs have different lengths (the outer one must run further diagonally). The inner track's diagonal run can become too short, or disappear and violate the curve rule, and the outer one's turn point lands on a tile the centreline did not use. A simple per-piece shift leaves gaps and overlaps at each corner, makes the gap between tracks wrong or not a whole number of tiles, can put the tracks on crossing tiles, and gives each track its own terrain and bridge situation. A shifted bridge may not line up (heads on different tiles), a shifted tile may be water or a house the centreline avoided, and S-bends and `curve_spacing` apply per track, so a legal centreline can give an illegal inner track. Each corner needs a rewrite rule (fix-up) per turn angle, hand and direction, then a re-check of every curve and terrain rule. That grows into a second router's rules without the guarantees. Wide spacing (gap 2-3 tiles) makes it worse because the diagonal offsets are longer.
- Option A is therefore only good as a fast first try that is checked and rejected on any failure.

Option B (true line state): the state is the head of the whole line: one shared position plus heading (the centreline or reference track), the curve-grammar state, and the set of track offsets from the notation. A move F, L or R advances ALL tracks. Each track's pieces for that move come from a per-move template (for a gap g and a track's side, the inner/outer diagonal lengths) rather than from independent search. Needed:
1. State: reference `x, y, trackdir` plus `u/hand/pair/prev_gap_ok` (same grammar, applied to the line as a unit, probably with the INNER track's spacing as the binding limit). Packed key stays about the same size, because tracks are derived from the reference. Add the track count and their offsets as constants in the request.
2. Successors: for each move, a template that adds N pieces (one per track, possibly several tiles per track in a turn). Needs a derived "move footprint": pieces plus the tiles they touch. Corner handling lives here, once and tested, rather than after the fact. The template table is the main new design work (per heading class and turn hand, for gap 0..3 or whatever the notation allows).
3. Validity per move: every piece of every track passes the in-bounds, heads, terrain `UsableAt`, and `ConflictsAt` checks. The rule is atomic: all or none. Bridges: B<n> moves all tracks onto parallel bridges (heads side by side), one of the `bridge_span_ok` and `SpanOk` checks per track (the junction already doubles bridges, see commit 86e223962d "doubled-bridge entry"). The ordering of heads must match across tracks.
4. Costs: sum of per-track piece, terrain, bridge and turn costs (turn cost once for the line or per track; decision needed), `Heuristic` scales by track count.
5. Goal: cursor tile reached by the reference with the heading continuing, or "closest tile to the cursor" as above.
6. `SelfCrossing` and `ConflictsAt` need the multi-track footprint, which currently allows only a parallel pair (same tile with Upper+Lower or Left+Right). For a line with gap 0 (L_R with adjacent) this is the existing allowance; for gap >= 1 there is no sharing at all. LL_RR (two per direction) needs same-tile pairs only in the 4-way parallel case, which the existing rule already allows in pairs.

Assessment: the existing router is about 440 lines and cleanly structured around `Successors`. Option B is a new router class (or a mode of `Router`) of about the same size, with the successors replaced by a template step. Roughly 60 percent of the machinery is reusable: node packing, the A* loop, `TurnAllowed`, terrain hooks, bridge-span checks, `RasterizeJunctionRoute` (per track), `AddRasterToLayout`. Recommendation: B for the final router, with A as a stepping stone only for straight and gently curving lines, behind the same interface (so tests carry over). Because template tables are the real design risk, first prove them with a fixed-script generator (no search) on L_R, LL_RR on flat terrain, then add search.

## D. Terrain

- `JunctionTerrain` (`junction_terrain.h`): a row-major grid `width x height` with `origin` in canonical coordinates, `At / UsableAt / CostAt / SpanOk`. Tiles outside the grid are Blocked. `UsableAt` takes a single `plane`.
- `MakeJunctionTerrain(anchor, rotation, mirrored, frame, margin)` (`junction_game.cpp:223`) fills it from the game: slopes via `GetTileSlopeZ`, class by tile type, clear cost via `QueryJunctionClear` (a `LandscapeClear` query-cost command per tile, the expensive part). It computes the grid from a `JunctionFrame` (`hub_x`, `terrain_origin_y`, `terrain_height`, `width`), which is a fixed rectangle in the junction's canonical frame rotated by `OrientJunctionVector`.
- For a painter in map axes: build a snapshot with `rotation 0`, `mirrored false`, origin at a map tile, and a frame sized to the bounding box. This works today if a `JunctionFrame` is built to give a rectangle (`MakeJunctionTerrain` is decoupled from the junction except through `frame`). Cleaner: split out `MakeTerrainRect(TileIndex min, w, h)` (map-axis, no frame), have `MakeJunctionTerrain` call it, and keep canonical = map offsets from the start tile for the painter.
- Problems for a long, thin, arbitrary corridor:
  1. Size. A bounding box of the start and the cursor can be 100x100 tiles when the line is diagonal; most is unused, and every tile costs a `LandscapeClear` query. Options: lazy per-tile fill (the router asks `At(x,y)`; the snapshot fills on demand and caches), or a corridor mask (fill only tiles within N of the start-cursor segment plus a margin), or a coarse bound with early-out. Lazy is the best fit, but `JunctionTerrain::At` is `const` and used by the worker thread (junction jobs build their terrain on the main thread and hand it over), so lazy fill must stay on the main thread: either route synchronously per drag step, with an expansion budget, or prefill a corridor.
  2. Single `plane`. A line over hills changes height: the junction fixes `plane` for the whole junction and uses bridges to cross dips. A line must allow slopes along its length. `UsableAt(x, y, plane)` therefore needs a plane that varies per piece. This is the deepest terrain change: the state gains a height (plane), pieces change plane on slopes (OpenTTD rail slopes: inclined track on a slope with `build_on_slopes`, or foundations), and cost per piece depends on the plane step. Decision needed: first cut with a single plane per bridge-delimited section (state carries plane; plane changes cost a foundation or are only allowed via an inclined slope rule), and tests on flat plus one-step hills.
  3. Existing own track at the start (the start piece) and on the way (crossing, join) are `Spannable` or `Blocked`; the painter's start tile has its own rail. `MakeJunctionTerrain` classes plain rail as `Spannable`, i.e. not usable; the painter's start tile must be treated as the start piece, not terrain. Same issue exists for the layout `starts` today, so likely handled.
  4. Rails of the player's own, other-company property, stations and so on all stay Blocked, good.
- Caching: the junction keys a cache on (tile, rotation, spec); the painter would key on (start piece, notation, cursor tile) and invalidate on map change (same as `cache.clear()` after a build, `junction_gui.cpp:~880`).
- Threading: junction searches run on a worker with a cloned snapshot. For the painter, run the search on a worker with a prefilled corridor snapshot, drop stale results when the cursor moves, as the junction `library_job` does. The first cut can be synchronous with a small `max_expansions` and a hover debounce, if the drag-time budget is small (a few ms).

## E. Proposed steps (test-first, each small)

Tests follow the existing junction unit tests style (stub pricing, fake poster, ASCII renderer `RenderJunctionAscii`).

- LP1: Notation to line spec. `ParseLineNotation` (reuse `ParseJunctionNotation`; extend for L_R, LL_RR, tracks per direction and gaps, with errors). Test: parse table, error cases. No game code.
- LP2: Line geometry templates. For a reference heading and each move (F, L, R) produce the per-track pieces for a notation (N tracks, offsets). Pure function, plus a renderer. Tests: straight lines in all 8 headings; one 45-degree turn each hand, for L_R and LL_RR at each allowed gap; the corner shapes are asserted as ASCII layouts. This is where the corner problem is solved. Gate: the checker's parallel and gap rules pass on every output.
- LP3: Line raster. A `LineRoute {start, heading, moves}` rasterizes to a `JunctionLayout` (tracks per tile) via the templates and merges with `AddRasterToLayout`. Test: round trip route to layout; the layout passes the existing checker rules on straights and turns.
- LP4: Line router on flat empty ground, no bridges: A* over the reference state with atomic multi-track moves, reusing `TurnAllowed` grammar. Goal is a set of exact end pieces first (like `FindJunctionRoute`). Tests: straight, single turn, S-bend, U-turn rejection by curve spacing, both L_R and LL_RR. Compare costs with the single-track router for N=1 (must match `FindJunctionRoute`).
- LP5: Obstacles and terrain. Wire `JunctionTerrain` (`UsableAt`) into all-tracks-or-none validity, existing layout conflicts, `ConflictsAt` for multi-track footprint. Tests: detour around a blocked tile, a line refused when any track hits water or a house.
- LP6: Bridges. `B<n>` moves with parallel (doubled) heads for all tracks; `SpanOk` per track. Tests: a river crossing for L_R and LL_RR; the head alignment matches the existing doubled-bridge entry (commit 86e223962d).
- LP7: Cursor goal. Replace exact goals by "closest approach to cursor tile, heading-aware", with a budget and an incremental result (best-so-far). Test: reaches the cursor tile on flat ground; stops short with a partial line when blocked; deterministic.
- LP8: Height. Per-piece plane (state gains plane), slope rules and foundation cost; tests with a one-step hill and a valley that needs a bridge. Gate: this decides the terrain model for D. If too large, ship flat-plane sections first.
- LP9: Terrain snapshot for corridors. Split `MakeTerrainRect` from `MakeJunctionTerrain`; map-axis rectangle with margin around the start and cursor, lazily filled or corridor-limited. Game-side test via the console (like `console_cmds.cpp:356`) on a loaded map.
- LP10: Line to build steps, cost and signals. `LineLayout` to `JunctionLayout` (reuse), D97 signal fill over the finished line (reuse the signal pass on each direction's path), `EstimateJunction` cost. Tests with the fake poster: step order, signal spacing at SD 4.
- LP11: UI shell. Toolbar widget (`WID_RAT_BUILD_LINE`, hotkey, cursor, `OnPlaceObject` to `VpStartPlaceSizing` with a new `DDSP_BUILD_LINE`), a small window with the notation field and railtype, start picking (existing track end: snap tile and heading; free tile: heading from the first drag direction). No routing yet; shows start and a straight ghost via `JunctionGhost`. Test: widget exists, abort restores state.
- LP12: Drag preview. `OnPlaceDrag` to route (debounced), `JunctionGhost::Set`, cost text, bad tiles in red; `OnPlaceMouseUp` to `JunctionSequencer::Start`. Reuses `GameJunctionStepPoster`. Test: ghost updates on cursor tile change; no route shows red with an error.
- LP13: Rig check. On the test rig (a hilly map): paint a doubled L_R line between two stations across a hill and a river, run trains both ways, confirm no deadlocks and that the signals match D97. Announce with the join command per the rig-watch rule.

## Open questions for the engineer

1. Start: snap to an existing track end only (join to a real piece, keep its Trackdir and gap), or also a free tile plus heading (from the first drag direction, or a rotate key)? For a free start, where does the line sit relative to the clicked tile (reference track, or the line's centre)?
2. Notation: reuse the junction's L_R / LL_RR text; what are allowed gaps between the tracks (spacing in tiles) and does the painter use the ML gap from the junction settings, or its own field? Can tracks per direction differ (LLL_RR)?
3. Curves: should the whole line obey the INNER track's `curve_spacing` (safest) or the reference's? Are S-bends allowed for a multi-track line (they need `s_bend_window` for every track)? Is turn_cost per line or per track?
4. Heights: is a line allowed to climb and descend (slopes, foundations, cuttings) in the first cut, or only flat sections plus bridges (the junction's single `plane`)? How much terraforming cost is acceptable? Tunnels: in or out?
5. Termination: when the cursor cannot be reached, show the best partial line, or nothing? Should the line end at the cursor tile with a free heading, or only continue in the current heading?
6. Endpoint joining: if the cursor is on an existing own track end, should the router make the exact join (a goal piece with matching gap), including mismatched gap (the joiner problem J3)?
7. Obstacles: may the line cross existing own track (and where: level crossing with a generated T, or only by bridge), and may it demolish trees/rocks/houses (priced, as `QueryJunctionClear`)?
8. Build: one undo unit would be nice; today the sequencer posts step by step with Retry and Cancel on failure. Acceptable for long lines (hundreds of steps), or batch straight runs into `BuildRailLong` commands for speed and a single Ctrl+Z-style removal?
9. Signals: D97 fill for the whole line on release always, or optional (toggle), and what about junction spacing of signals around bridges and curves? Fixed-distance mode (deferred in D97) needed?
10. Performance budget: the maximum line length and A* expansion cap per drag step; synchronous or worker-thread with a stale-result drop?
11. Multiplayer: the painter builds through the existing per-step commands (no new command), as the junction does; confirm no new network command is wanted.
12. UI placement: second panel in `BuildJunctionWindow`, or a new window; same toolbar button with a mode switch, or a separate button?
