# RECON-prio-rule: what makes a prio length sufficient (RP0, read-only)

Read-only recon. Nothing was built or run; numbers in section 3 for the 6 speeds are NOT computed (INFERRED structure only). Line numbers are from the checkout at f2a0cc0fe5.

## 1. What SizeJunctionPrio does (src/junction_generator.cpp:1940-1964)
1. Copies the spec, sets prio_tiles = max(1, spec.prio_tiles) (:1943).
2. Loop: `GenerateJunctionUnchecked(copy, nullptr)` (:1945, defined :1855): the full old-generator sweep on flat ground: heights ml_gap+5..ml_gap+20 (:1884-1885), per height 2 crossing costs x (4x4x3 symmetric + 2 parallelogram) = 100 builds (AddJunctionSweepParams :1826), picks the best-scoring rule-clean layout. No layout: returns {0, error} (:1946). This is where it fails at 140/160 (section 4).
3. `PrioTimingsOf(layout, copy)` (:1810): checker context, the 6 T paths, then `JunctionPrioTimings` (src/junction_throughput.cpp:520) with design speed JunctionTerminalSpeed(train), tl.
4. For each prio merge, `SimulatePrioTiming` (throughput.cpp:392-503) is a train simulation on the real layout (not the checker, not a formula): it runs the joiner from rest at its Entry signal with StepJunctionTrain until it holds design speed and its tail is past the merge (cap 20000 ticks, :319); records the intervals each block is held (body = head - tl tiles, virtual signals every sd tiles past the exit); runs an ML train at constant design speed; for every signal with a held next block, the ML starts that cross it inside a held interval form a range [low, high]. `required_distance` = merge piece start - smallest low over all ranges (:498); `ml_delayed` = some range has low <= coverage edge (edge = merge start - prio_tiles tiles).
5. Delayed: `next = required_distance / JunctionProgressPerStraightTile() + 1`; `wanted = max(prio_tiles+1, next)` (:1958); above MAX_PRIO_TILES = 32 -> PrioTooLong (:1801, :1959). Else returns prio_tiles (:1956).
So the verdict is the exact timing model; each iteration re-sweeps the whole generator (about 7 s, STATUS).

## 2. Rules that make a prio length legal or sufficient
Legal (geometry only, checker; no minimum except the ML-merge exists):
- CheckPrioReach (src/junction_rules.cpp:1535): limit = 2 * prio_tiles units (:1540); every ML piece within the limit before the merge piece (plus one piece beyond a signalled end) must, as a one-tile train, settle the joiner's Entry red (SettleSignals :1618). The length is only an input here; it never says how long it must be.
- CheckPrio (:1054-1363): one prio row beside the ML, first join on the merge tile, one join per block in coverage, no ML split in coverage + one segment (D108, G9c), signal types (Exit farthest, Combo else).
- D148/D148a (DECISIONS.md:158,160): E side split at x_join - x_s >= prio_tiles + 1 (window start x_s + prio_tiles + 2); odd prio_tiles >= 5 need +1 (join parity: the pass refuses adjacent joins).
- DESIGN-N3 §2 T3 (docs/junction-tool/DESIGN-N3.md:16): no curve within 2p units before a prio merge, no split within 2p+1.
Sufficient (timing, not in CheckJunctionRules): D119 "ML delay strictly zero" (DECISIONS.md:126), enforced as `ml_delayed || timed_out` in GenerateJunction (generator.cpp:1927 prio_strict) and in SizeJunctionPrio. D137a (:146): coverage in whole tiles, sized by exact timing. D29/D31 (:35,:37): "shortest mathematical answer" from the acceleration model. Coop R27 (RULES-coop.md:54): prio behind the merge covers the joiner's whole acceleration run from standstill to top speed; R26: a bit in front; R25: segments <= shortest TL. None gives a formula (RULES-coop.md:10).

## 3. Closed form?
Mostly yes. The needed coverage in distance is, from SimulatePrioTiming's own definition:
  need = max over signals s_k and held intervals [first_k, last_k] of ( merge_start - s_k + d_ML(last_k) )
where d_ML(n) = n ticks at design speed v (constant, AdvanceSpeed*2 per tick) and last_k is the tick the joiner's tail leaves block k. For blocks beyond the merge the joiner is still accelerating while the ML runs at v, so the binding case is the ML catching the accelerating joiner with one signal gap between them. That is exactly what `JunctionPrioLength(joiner, design_speed, tl, sd)` computes (src/junction_train_model.cpp:118-138): joiner from rest with StepJunctionTrain until it reaches v; max_deficit = max(ml_progress - joiner_distance); result = ceil(max_deficit / tile) + tl + sd tiles. design speed is first clamped to min(v, max_speed, terminal speed) (:121). Cost: one loop of StepJunctionTrain until the speed reaches v (about 10^3 ticks), microseconds to a millisecond. It already exists, is used only by the console `junction_train` (console_cmds.cpp:608) and by tests (tests/junction_throughput.cpp:336, where rounding it up to whole TL is shown enough on a hand-made merge).
Inputs: train (power, TE, mass, drag, max speed), design speed v, tl, sd. All spec fields, no layout.
What it leaves out (INFERRED from the code): (a) the exact joiner start offset: the sim starts the joiner at its Entry signal, entry_to_merge (corner pieces, straight run) shifts the joiner's position relative to the merge and so the first held interval; the formula assumes the joiner starts at the merge; (b) the signal phase: s_k positions relative to the merge tile (the pass places them; D148a parity), up to sd tiles; (c) corner speed of the joiner (the model uses straight distance); (d) rounding to a tile. So JunctionPrioLength is a closed-form estimate within about sd + a few tiles; the exact minimum needs the template's own geometry (entry_to_merge, block edges), which the node model derives by rule (D193), so it can be added to the formula as constants of the template, not a search.
Values: NOT computed here (no build; the existing console command needs a vehicle). Measured for the train 14194,1090000,561,25: 100:9, 120:8, 140:10, 160:11, 180:12, 196:14 (STATUS.md:2); test spec prio_tiles 14 (generator.cpp:106). The measured series is not monotone (9 then 8), while JunctionPrioLength is monotone in speed (tests/junction_train_model.cpp:103-107), so the layout term (a)/(b) moves the answer by at least 1; INFERRED cause: curve spacing grows with speed (2,3,4,5,6,7 tiles, DIAG-flat-speed.md Q1), which changes entry_to_merge and block phase. To obtain the 6 formula values: call JunctionPrioLength(train, v, 5-or-tl, sd) for each v, in a 10-line scratch test (about 1 s).

## 4. Why the sweep fails at 140/160 (DIAG-flat-speed.md Q1-Q2)
Not the timing: GenerateJunctionUnchecked returns NoLayout (error 3), SizeJunctionPrio returns {0, NoLayout} at once (:1946). Causes in the old generator: curve spacing 4 (140) and 5 (160), flat height cap g+13 (junction_generator.cpp:1096), and the cost-led router laying cheap long rail that blocks B->S ("no valid skeleton" at h12, "B->S failed" at h13-14); raising the cap builds 140 at h15, 160 at h17. Prio 10..16 changes nothing there. So the failure is in the generator the sizing borrows, which the node model (N0c2) no longer needs.

## 5. Open questions for the orchestrator
1. Accept `JunctionPrioLength(train, v, tl, sd)` (+ template constants for entry_to_merge and signal phase) as the rule, or must prio_tiles equal the exact SimulatePrioTiming minimum? With D193 the template could compute the exact answer by running JunctionPrioTimings on the node-model layout (one solve, no sweep): is that acceptable on the hover path (< 100 ms)?
2. Units: prio_tiles is straight tiles, JunctionPrioLength is tiles; the tests round up to whole TL (tests/junction_throughput.cpp:337). Which does D137 (whole tiles, not whole TL) rule? Presumably tiles.
3. Parity: D148a needs odd prio_tiles >= 5 to shift the E window by 1; should the rule round the length up to an even value instead?
4. Is the formula's assumption (joiner starts from rest at the Entry) the intended physics? A joiner already moving (Entry green) makes the need shorter; the sim assumes standstill (R27).
5. sd (signal spacing) is a spec field; does N0c2's template fix the ML block edges so the signal phase is known before sizing?
6. Should the formula be checked against SizeJunctionPrio on the 6 speeds and the test spec (14) in a scratch test before replacing the sweep? Recommended; cost one test.
