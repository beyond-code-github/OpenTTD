## 1. Slope effect, realistic model (the default)
- `train_acceleration_model` default `Realistic`: table/settings/game_settings.ini:159-168 (def at :163). Branches in `Train::UpdateSpeed`: train_cmd.cpp:3080-3088.
- `train_slope_steepness` default 3 (percent), range 0..10: game_settings.ini:186-195; read by `Train::GetSlopeSteepness` train.h:321-324. Used only by the realistic model (settings_type.h:608 comment).
- Per-part slope force (N): `cached_slope_resistance = part_weight_t * steepness * 100` (ground_vehicle.cpp:85-88). At 3% that is 300 N per tonne.
- Total slope force = sum over ALL parts: +force for each part with GoingUp, -force for each with GoingDown, 0 otherwise (ground_vehicle.hpp:109-121). So the force is per part: a train partly on a ramp feels the fraction of its weight that is on sloped tiles. Up and down parts cancel (crest/valley).
- Flag setting: when a part enters a tile, `UpdateZPositionAndInclination` (ground_vehicle.hpp:125-146) resets both flags (:133), then, only if `TileMayHaveSlopedTrack()` (track is X or Y, train.h:348-351), compares tile-centre z with edge z and sets GoingUp/GoingDown (:135-143). Called per part at a new tile, train_cmd.cpp:3631 (`UpdateInclination(new_tile != old_tile, false)`; wrapper ground_vehicle.hpp:~222). So inclination is per whole tile: a part is "on the slope" for the whole of every sloped tile it is on. Flags are swapped when the train reverses (train_cmd.cpp:1628-1641).
- Force balance (ground_vehicle.cpp:105-179): resistance = axle 10 N/t (:94) + mass * rolling 15*(512+v)/512 (train.h:309-315) + air 14*drag*v^2/1000 (area 14, train.h:272-276; formula :143-144) + slope (:146). Tractive force = min(max_te, P*18/(5v)), P in W = hp*746 (:114, :152-157). Acceleration = (force - resistance)/(4*mass), min -1 if force < resistance (:165-173).
- So a part-on-slope force needs spare tractive force. Slope below the line speed only drops speed to the equilibrium where force(v) - flat_res(v) = slope force; it does not stop the train unless slope force > te - res at low speed (kickoff at v=0 uses max(force, 8*mass + resistance), :158-162).

## 2. Original model
- No slope force: `UpdateSpeed` uses fixed `acceleration` (train_cmd.cpp:3083). `GetCurveSpeedLimit` returns unlimited (:328), so no curve limit either.
- Fixed slow-down in `AffectSpeedByZChange` (train_cmd.cpp:3158-3171), called only for the FRONT part (`prev == nullptr`, :3633-3636) every position step where z changed: up: `cur_speed -= cur_speed * z_up >> 8`, z_up = 256/4 = 64 (25%, table :3146-3150, same for all three types incl. maglev); down: `+= z_down = 2`, only if <= `cached_max_track_speed`.
- INFERRED per tile: z changes by 1 on alternate pixel steps (ground_vehicle.hpp:~195-216), 8 z units per level (tile_type.h:18), so a one-level tile gives up to 8 applications. The effective loss per tile is large and compounding; not derived. The tool should treat the original model as out of scope or measure it.

## 3. Track geometry on slopes
- Settings: `construction.build_on_slopes` default true (world_settings.ini:372-375). `GetRailFoundation(tileh, bits)` rail_cmd.cpp:311-370; check in `CheckRailSlope` rail_cmd.cpp:398-404: an Invalid foundation always fails; a non-None foundation fails if build_on_slopes is off (error "land sloped in wrong direction"); a foundation costs `Price::BuildFoundation` (:407).
- No foundation needed (rail_cmd.cpp:260-280, indexed by slope; one-corner-raised slopes take only the corner-cut track on the lower side, the table row is `Right/Upper/Left/Lower`): flat any track; the four two-corner "incline" slopes SW/NE take only X, NW/SE only Y (table entries 3, 12, 6, 9). Other tracks on those, and all other slopes, need a foundation.
- With foundation: one-corner-raised slope + X or Y track gets `InclinedX/InclinedY` (rail_cmd.cpp:354-360), i.e. the track still climbs; any other piece (curves, upper/lower/left/right halves, combined tracks) gets `Leveled` (:333-363, table :283+) if it fits, else Invalid. Steep slopes: only X/Y inclined, a corner halftile, or SteepLower/Both (:315-331).
- Consequence: only straight X or Y track (`TileMayHaveSlopedTrack`) climbs. Curves, switches (multi-track tiles) and diagonals-across-tile are flat (leveled foundation) or invalid. Rising by n levels along a straight needs n sloped tiles, one level (8 z) per tile (an incline slope raises one edge by one level: the SW/NE/NW/SE slope shapes, tile_type.h:18).
- Signals: no slope check found in rail_cmd.cpp:1070-1140 (read; nothing slope-related). INFERRED: a signal may sit on any tile the track may sit on, including an inclined X/Y tile; not checked in `CmdBuildSingleSignal`'s callees.
- Bridge heads: `GetBridgeFoundation` tunnelbridge_cmd.cpp:111-118: no foundation on flat or along-axis incline; `CheckBridgeSlope` :209-226 allows only flat or the single valid incline for that end (north end NE/NW, south end SW/SE, :216-222), else error. `HasBridgeFlatRamp` :127-131: a head on an incline is a sloped ramp (non-flat), else flat ramp. A foundation is allowed only with build_on_slopes (:465, :472, :481). Bridge height from heads: the middle must clear terrain (:489-500).
- Tunnel portals: start tile must be an exact incline slope (`GetInclinedSlopeDirection`, slope_func.h:249-258; tunnelbridge_cmd.cpp:670-672), end tile slope must be the complement (:742). A portal cannot be on flat ground. In the tunnel the train is on flat z (YAPF: "tunnel entry/exit doesn't slope", yapf_costbase.hpp:39).
- Depots: sloped only if `CanBuildDepotByTileh(dir, tileh)` (rail_cmd.cpp:~985-989); out of scope for junctions.

## 4. Derivation sketch (for a junction ramp rule)
Notation (all from the game): m total mass (t), P hp, te max T.E. (N), d air drag, v line speed (cur_speed units), tl train length in tiles, s steepness (3), a ramp of n sloped tiles climbing n levels.
- Spare force at v: S(v) = min(te, 746*P*18/(5v)) - [10m + m*15*(512+v)/512 + 14*d*v^2/1000] (ground_vehicle.cpp:139-157).
- Parts per tile: a standard part is VEHICLE_LENGTH 8 (vehicle_type.h:67) of TILE_SIZE 16 (tile_type.h:15), so about 2 parts per tile; weight fraction on the ramp is about min(n, tl)/tl for a uniform consist (INFERRED, true weights are per part, so loco-heavy consists vary; a ramp of n >= tl tiles puts the whole train on it).
- Slope force on a train fully on the ramp: F_slope = m * s * 100 (N). Holds line speed iff F_slope <= S(v). Otherwise speed settles at v_eq with S(v_eq) = F_slope * min(1, n/tl). A short ramp (n < tl) loads only a fraction, but the climb is short, so speed lost is also less; steady state needs n >= tl.
- Worked, D138 train (14194 hp, 1090 kN, 561 t, drag 25, v 196; junction_generator.cpp:110-114): flat resistance 30.7 kN, tractive 194.5 kN, spare 163.8 kN. Full-train slope force at 3% = 168.3 kN, so v_eq = 192 (4 below 196). Quarter of the train on the ramp (42 kN): 357 (no loss). Half (84 kN): 289 (no loss). The maximum grade the train holds at 196 with the whole train on the ramp is about 2.92% (spare / (m*100)). INFERRED: computed by hand from the formulas above, not simulated. So this train is almost unaffected; ramp rules matter for weaker or heavier trains and lower speeds (S falls as v rises past the power-limited point).
- Down slopes help (GoingDown subtracts, ground_vehicle.hpp:116-118) and are never the problem; braking uses `-force - resistance` with the slope term included (:174-177), so a descent lengthens stopping: INFERRED relevant to prio signal coverage on a down ramp, not derived.
- Curves vs slopes: a sloped tile is X/Y track only (train.h:348), so a curve cannot be on a ramp tile. The curve speed limit (train_cmd.cpp:321-375, realistic only :328) depends on directions of consecutive parts and is not affected by slope; it caps max speed (`GetCurrentMaxSpeed` :397-401), slope only changes force. Interaction is in time and energy: a curve that cuts the train to curve speed just before a ramp starts the climb at lower v, where te limits (not power) and the climb accelerates harder, so a curve before a ramp costs speed to recover while a curve after a ramp costs nothing extra. A curve inside the span of tl tiles from the ramp end matters only through the curve limit already derived (DeriveCurveSpacing, junction_generator.cpp:90-100; JunctionCurveGaps junction_chain.cpp:25-43).
- Inputs the spec already has (junction_train_model.h:14-22 JunctionTrainParams): power_hp, max_te, mass_t, air_drag, max_speed; spec also has tl, reference_speed, curve_speed (junction_generator.h:42-46). That is enough for S(v), F_slope, v_eq. Missing: slope steepness setting (default 3, read from game), the acceleration model (original makes the force model invalid, so either require Realistic or measure), per-part weight distribution (a uniform approximation or the picker's per-part weights), and whether the line speed is the reference_speed or max_speed.
- Rule shape (to be settled by Pete): derive max ramp length in tiles from the loss threshold, for example the longest incline (n levels) for which v_eq >= reference_speed; for the default 3% and the D138 train that is unbounded up to 2.92%, i.e. the whole-train case already gives 192 so a loss threshold is needed.

## 5. YAPF slope cost
- `rail_slope_penalty` default `2 * YAPF_TILE_LENGTH` = 200 (pathfinding_settings.ini:162-166; YAPF_TILE_LENGTH 100, pathfinder_type.h:16; struct field settings_type.h:548).
- Charged per tile entered uphill: `SlopeCost` yapf_costrail.hpp:98-102, summed in segment cost :403-404. `stSlopeCost` (yapf_costbase.hpp:27-45): only diagonal trackdirs; a bridge head is charged on entering a non-flat ramp, not on leaving (:30-36); a tunnel never (:39); other tiles by `IsUphillTrackdir`. Downhill costs nothing. Cost hint: 2 flat-tile equivalents per uphill tile, so a signal block planned around a ramp should not rely on the pathfinder to prefer a flatter alternative unless it is within about 2 tiles per level.
