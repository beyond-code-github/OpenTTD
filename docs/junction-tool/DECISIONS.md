# Junction tool: decisions

Rulings made with the engineer. Briefs point here; a recorded decision is not re-asked.

| Id | Question | Ruling | Scope |
|---|---|---|---|
| D1 | Where does the feature live? | Core C++ in a fork of OpenTTD. NewGRF can't do it; a Game Script lacks the UI. Deployment as a binary patch is fine; upstream acceptance is not a goal. | Whole project |
| D2 | What does the player do? | "Select from an in-game junctionary but then maybe you tag the connection points on an existing mainline and it figures out how to join them up in the smallest most organic footprint." Not generation from a prompt. | Whole project |
| D3 | How are multi-track links routed? | "We wouldn't treat them as ribbons but we would constrain the search space with certain conditions." | Solver |
| D4 | How is the work done? | Test-first, outside-in, run through the agent-orchestration skill. | Whole project |
| D5 | Where do the plan files live? | `docs/junction-tool/` on branch `feature/junction-tool`. | Whole project |
| D6 | How do the solver's tests get terrain? | "B is fine if that matches the house style." It does: an abstract base class with pure virtual members and a test subclass, as `FontCache` / `MockFontCache` (`src/fontcache.h`, `src/tests/mock_fontcache.h`). The solver reads terrain only through a small interface; the game implementation wraps the real map and reuses the game's own slope/foundation rules; tests use a hand-built implementation. | Solver and its tests |
| D7 | How is a solved plan built? | "A also makes sense, we'd just work hard to make sure it wasn't going to fail or that we could react to failures." Post ordinary build commands in sequence. Validate the plan up front, and handle a failed command by stopping the sequence and telling the player what was and wasn't built. | Milestone 1; revisit when junction cores arrive |
| D8 | Does rail type matter? | "This needs to work with different types of rail depending on which tool is selected - so that may determine the interface design." The rail type of the active rail toolbar is an input to every solve. Rail-type rules (build cost, 90-degree turn flags, compatibility with existing track, level crossings) live in a rules component the solver queries, separate from the terrain interface. The terrain interface reports the rail type of existing track so the rules can judge it. | Solver, preview, build |
| D9 | Must cost be known before building? | "We'll definitely need to assess cost up front as that's the most obvious failure case." The exact cost (sum of test-only runs of every build command) is shown against the money available before the player confirms, and building is refused if it can't be afforded. Re-checked immediately before building starts. | Every milestone |
| D10 | Terraforming in M1? | "Leave for M2." M1 routes over existing terrain using foundations only; terraforming is milestone 2. | Milestone 1 |
| D11 | Build order | "I see two build modes - one where a basic pre-built junction is selected and then placed - the ghost and price updates as the mouse moves similar to RCT. The other is the endpoint selection method. We could build the pre-built aspect first and just require flat ground in the first iteration?" Agreed: M1 is pre-built placement on flat ground; endpoint linking (the solver) follows. Supersedes the confirm-window question. | Milestone order |
| D12 | Rail-type join rule | Deferred to the endpoint milestone; a freestanding junction is built in the tool's rail type. | Endpoint milestone |
| D13 | Ghost graphics | Transparent real sprites: the selected rail type's own track, signal and bridge sprites, semi-transparent, tinted red where invalid. | M1 onward |

| D15 | Rotation and mirroring | Rotate and mirror, by hotkey, in M1. | M1 onward |
| D16 | Where junction definitions come from | "Procedural is a great starting point and will be easier to extend for terrain etc." Junctions are produced by C++ generators (one per family, parameterised e.g. by TL) into an in-memory junction description; placement, ghost, pricing and building consume only that description. A file format may come later as a second producer. | M1 onward |
| D17 | First junction family | "So the first junction should be a L_R t-junction with CL 3 and doubled bridges." Exact geometry (meaning of CL, bridge arrangement, signals) to be confirmed with the engineer before the generator is specified. | M1 generator |
| D18 | What CL means | Curve Length: the minimum straight track (orthogonal or diagonal) between two consecutive 45-degree turns in the same direction; CL3 = 3 tiles. Matches the game: `Train::GetCurveSpeedLimit` (`train_cmd.cpp:321`) penalises short distances between same-direction 45° bends within a train; an S-bend (one left, one right) has no penalty; a 90° bend caps speed at 61. How diagonal pieces are counted is still to be confirmed. | Generators, later the solver |
| D19 | What "doubled bridges" means | "Split, 2 bridges, merge": each track that crosses the mainline splits into two parallel tracks, crosses on two side-by-side bridges, then merges back. Reason: vanilla can't signal bridges (`CmdBuildSingleSignal` needs a plain rail tile, `rail_cmd.cpp:1078`), so each bridge is one long block; two bridges let trains alternate. | Generators |
| D20 | Signal type | "I think people usually use one-way block signals, but consider the CPU implications as discussed." Default one-way block signals; signal type is a generator parameter. The junction is fully grade-separated, so path signals add no capacity there. | Generators |
| D21 | Approach/exit leg signalling | "Parameter, default SD2": signal distance is a generator parameter (default 2); leg length is also a parameter. | Generators |
| D22 | Movements and line spacing | "The mainline goes straight through, and the branch can be joined/left from either direction" (full T: all six movements). "We also need to treat the number of spaces between rail directions as configurable": the gap in tiles between the two directions of a line is a generator parameter. | Generators |
| D23 | Which tracks are bridged | "I think commonly the bridging is done on the mainline rather than on the branch lines, so that the joins can pass underneath." The mainline track that a turning movement must cross is carried on a bridge; the branch connections stay at ground level and pass under it. How this combines with D19 doubling is to be settled with the layout. | Generators |
| D24 | Order of splits and merges | "Splits must happen before merges": along every track, a train meets any split before any merge. A hard rule for every generator (and later the solver). | All generators |
| D25 | Priorities (prios) | "We need to also consider prios. Prios are signal loopbacks designed to only allow trains to merge when there's space on the mainline." Merges onto the mainline get a prio: a parallel unused track joined to the mainline track at intervals upstream of the merge, so a mainline train occupying it holds the merging signal red (wiki: Junctionary/Priority Merge, "Priority Merges Using Extra Track"; works with block signals). Segmented so the shortest train always covers a connection. Details (which merges, side, length) to be settled. | Generators |
| D26 | Who designs the layout | "To be honest, we should be letting the math design the junction." The generator derives the layout from the topology, the rules and the parameters (e.g. it decides which connection bridges over which), rather than a hand-drawn layout. Approach to be agreed. | Generators |
| D27 | Which merges get prios | "Mainline merges only." | Generators |
| D28 | Prio side | "Outside": on the far side of the mainline track from the other direction. | Generators |
| D29 | Prio length | "Joining trains must not be slowed down so it will need to be somewhere between 1 and 2 TL but take the shortest mathematical answer." Derivation to be agreed. | Generators |
| D30 | What "best layout" means | "Fewest tiles, then cost." | Generators |
| D31 | Train data for prio length | "Player picks a train": an engine and wagon count (TL); the generator uses OpenTTD's acceleration model to compute the shortest prio that keeps joining traffic flowing. | Generators |
| D32 | Bridge arrangement vs evil mode | "We can consider any option based on throughput, but allowing doubled ML bridge or bridging connections instead is preferred depending on level of traffic. Remember, we may be building a SL-SL hub even where throughput is not important." The generator considers single ML bridge, doubled ML bridge (block signals, D19) and bridging the connections over the ML, and picks by a traffic-level target; low-traffic (e.g. SL-SL) junctions don't need the high-throughput variants. Needs a throughput measure (to be designed). Refines D23. | Generators |
| D33 | Prio signals | "If there's really no difference, follow the signal-type parameter. Otherwise choose based on available space and overall cost." Generator builds the prio in the junction's signal type (pre-signal prio for block, path-signal prio for path); where the variants differ, compare them by footprint then cost (D30). | Generators |
| D34 | Prio longer than 2 TL | "Use the math, warn": build the length the acceleration math requires, even beyond 2 TL, and say so in the placement tooltip. Refines D29. | Generators, placement UI |
| D35 | R47 bridge length | Not a fixed rule: bridge types have their own min length and speed (`table/bridge_land.h:774`); fast types need ≥2 middle tiles. The generator picks the cheapest type at least as fast as the rail type and the length follows. (Orchestrator ruling from code; overrides RULES-coop.md R47 wording.) | Generators |
| D36 | How diagonal pieces count for CL | Traced in code: every train part moves one step per `TrainController` call (`train_cmd.cpp:3379-3383`, driven per step at `:4138-4140`); a straight tile is 16 steps, a diagonal piece 8 (`GetNewVehiclePos`, `vehicle.cpp:1804`); the curve check counts wagon lengths (8 steps each). So a diagonal piece = ½ tile for CL: CL3 on a diagonal = 6 pieces. For travel time a diagonal piece = ⅔ of a straight tile (2048 vs 3072 progress; the whole train pays the front vehicle's step cost). Resolves the open point in D18. | Generators, 1c physics |
| D37 | Which side trains run on | "We could take train side direction from the road rule setting, or we could provide the option directly in our build dialogue alongside CL/TL etc." Combined: a left/right option in the build dialogue, defaulting from the game's road-side setting. Generated layouts are right-hand; left-hand is the mirror. | Generators, placement UI |
| D38 | Line spacing notation | "LL_RR is two lanes directly adjacent either side of a one tile gap. L_L__R_R would be two tile gap and one between the two lanes in either direction. This is a guideline rather than a mandatory distance - it's always better to build *with* the terrain." Each `_` is one empty tile; the notation string is the line-profile parameter for each leg. Spacing may legitimately vary along a line (climbs, coastline, widening before a junction), so later milestones treat it as a default, not a constraint; on flat ground (M1) the legs use it exactly. | Generators; terrain milestones |
| D39 | Traffic level | "I'm not sure how to express traffic level just yet." Open; to be settled in the 1c plan. | 1c |

| D67 | CL is derived, not set (revises D64's CL setting, D18's CL parameter) | "CL should be derived from the template train properties instead of being specified directly." From `Train::GetCurveSpeedLimit` (`train_cmd.cpp`, realistic acceleration): a penalty only applies when one train covers two or more same-direction 45° bends at once; the limit is `232 - (13 - s)²` for average bend spacing `s` in half-tiles (straight tile 2, diagonal piece 1; clamped 1..12), plus half per point of rail-type `curve_speed`, plus 20% if tilting; bends ≤ 1 wagon apart cap at 88; one left + one right is exempt only when they are the only bends under the train (engineer: "S-bends only count as free curves if there is one of them per TL"; `curvecount[0] == 1 && curvecount[1] == 1`). Derived CL = the smallest spacing whose limit ≥ the train's max speed, capped at TL (bends further apart than the train never penalise). 1b inputs: TL from the window's stand-in control, max speed from D45's fastest buildable compatible engine, the rail type's `curve_speed`, no tilt. 1c swaps in the picked train. The original acceleration model has no curve limit (open item in 1c). | 1b generator, 1c |

| D69 | Save compatibility | "We need to make sure that we don't end up with save games that don't work with or without the patch." Hard rule: the fork never changes the savegame format: no new game settings, map bits, pool objects or chunks, and no savegame version bump. Stock builds keep unknown `openttd.cfg` keys (`SaveToConfig` only removes known moved settings, `settings.cpp:1505-1525`), so switching builds is safe too. Any future feature that seems to need saved state must come back to the engineer first. | D71 | Waiting room and deadlocks | "This is somewhat dependent on traffic - The key aspect is that traffic joining a SL should never block the ML.
