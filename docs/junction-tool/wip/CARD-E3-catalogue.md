# CARD E3-1: the gadget catalogue as data, verified once (orchestrator, 2026-11-21)

Implements PLAN-sss-v2 E3 first step; DESIGN-sss-v2 §3.2 item 2 (gadgets) and §7 Q1 (parametrisation, hull). Inputs: wip/RECON-gadgets.md (what the composer builds today), DESIGN-components C2-C9, D311, D330, D355, D384, D388.

## What changes from the composer (recon §1, §5)
Today each primitive is a code path in `MappedComposer` writing rows into one per-hub MILP; tile sharing is allowed by scattered exemptions (`ok_pair`, `at_shared_node`) and clashes are found by a lazy loop. In v2 a gadget is **data**: a fixed internal shape per type and lane count, its ports, and named parameters; it is **verified once** against the real tile rule, and that verification is the only place tile sharing is allowed. Shape picks the gadget and its orientation; Slots only sizes its parameters.

## The data form (orchestrator design)
- `PlanarGadget`: type, lane count n, side sigma (mirror), and per internal track a start point and a piece list in the gadget's frame (heading relative to the spine heading h: h + t, t in -2..2; length in half tiles; kind ground / deck head / deck middle / tunnel); ports (per attached spine: in or out, its lanes, the port point and heading); named parameters with lower bounds (and exact ones); declared shared tiles (the coop tile sharing it relies on: join half pieces, D353 diagonal halves, trident).
- Generated by rule from D330's primitives per type and n (`MakePlanarGadget(type, n, sigma, options)`), never hand-drawn per hub (D326, D330). The composer's shapes (recon §1) are the starting point, with its known gaps fixed where a ruling says so (D355 split gaps, D384/D349 rows following their lane).
- **Hull:** the gadget's outermost tracks on each side are its walls for the free-face cells; everything between them is rigid and verified.

## Parameters are cuts (the guarantee that makes "verified once" true)
- A parameter lengthens, by the same amount, one piece on every internal track that a line across the gadget meets, all those pieces parallel. The two halves of the gadget then move apart rigidly, so no clearance inside shrinks: verifying the shape at its least values covers every value.
- A freedom that is not a cut (a D355 split gap that moves one leg sideways) is verified on a sampled range and listed by name as an exception, until its own argument exists.

## Verification (the test that is the catalogue's promise, H15)
- `[planargadget]`: every gadget type, n = 1..4, sigma = +-1, spine heading axis and diagonal, at least values: lay each track's pieces on the tile grid (`RasterizeJunctionRoute`), check every pair of pieces of different tracks with the real tile rule (`JunctionTracksMayShareTile` plus the touching rule of `PiecesClash`, shared with `PlanarGeometryClashes`), allowing only the gadget's declared shared tiles. Plus each non-cut parameter on its sampled range.
- No tool does this today (recon §3): the first build step is this harness, test-first, on the simplest gadget (the one-lane split).

## Order of types (by what T2 and PSG 197 both need; recon §4)
1. One-lane split and one-lane merge (197: 62 nodes, all one-lane; T1).
2. Arm end (port stub, side gaps).
3. Crossing stack, tunnel and bridge, groups of 1-3 separators with per-lane crosser sets (197: 50 tunnels, 18 groups).
4. n-lane fray and join with their internal order swaps (T2, T3), prio row (D384 exact, follows its lane, D349), doubling (C6 parallelogram).
5. Stand-alone order swap (C8; 197 has up to 13 candidate same-channel crossings, to confirm with the channel builder).

## The decision for Pete (RULED D398: option B, per node)
- **Context:** a site where several lanes of one bundle split (T2's fray: two lanes, each splitting, the straight lanes bridging the diverging ones) can be one gadget per node or one gadget per site.
- **Options:**
  - A. **One gadget per site, generated per lane count** (recommended): the n splits and the order swaps between them are one verified shape, so their tight tile sharing is checked together; the catalogue is per type x n (n = 1..4).
  - B. **One-lane gadgets only:** a site is n one-lane gadgets side by side plus crossing gadgets between them; fewer shapes, but the clearance between them is then a Slots matter (cells inside a fray), which is what v2 moved away from.
- **Recommendation:** A. It is D388's "verified once per lane count" and D311 (2)'s "one Join and one Fray type, composed inside their stretch from the primitives"; 197 needs only n = 1 anyway.
- **Prior art checked:** D311, D330, D388, recon §1.2 and §1.4 (today's n-lane fray and join are exactly such per-site shapes).
- **Reversible:** yes (the catalogue is generated; B is A at n = 1 with the site split).
