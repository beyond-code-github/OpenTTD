# Recon: junction generator (milestone 1b)

Read-only recon, 2026-11-07, branch feature/junction-tool. Paths under `src/`. "(inferred)" marks anything not read directly from code. Placement/ghost/bridge-price facts are in `RECON-placement.md` and are not repeated.

Vocabulary trap: OpenTTD calls `Track::X`/`Track::Y` "diagonal" (`IsDiagonalTrack`, `track_func.h:514`). The plan's "straight" is that kind of piece; the plan's "45° / diagonal run" is built from `Upper/Lower/Left/Right` pieces (inferred from `_next_trackdir` and `ValidateAutoDrag`). The generator code should name its own helpers (`IsAxisTrack`, `IsHalfTrack`) to avoid mixing the two.

## 1. Signals

- **(a) Pipeline.** `JunctionSignal{offset, facing, type, variant}` becomes `JunctionSignalStep{tile, facing, type, variant}` (`junction_layout.cpp`, `MakeJunctionBuildSteps`, signals pushed last, after rail and bridges). `GameJunctionStepPoster::Post` (`junction_game.cpp:179-180`) posts `Commands::BuildSignal` with `TrackdirToTrack(s.facing), s.type, s.variant, convert=false, skip_existing=false, ctrl=false, cycle_start=Block, cycle_stop=Block, num_dir_cycle=0, signals_copy=SignalAlongTrackdir(s.facing)`.
  - The signal type is passed through unchanged, so Entry/Exit/Combo/Path/PathOneWay all reach the command. Nothing in the pipeline filters them.
  - With `signals_copy != 0` the present-signal bits are set to exactly the given side (`rail_cmd.cpp:1175-1180`). The `KillFirstBit` one-way fix-up for PBS types only runs in the `signals_copy == 0` branch (`:1148`), so `PathOneWay` gets the same exact one-direction bit. Fine for both block and path types.
  - `SignalType` values: Block 0, Entry 1, Exit 2, Combo 3, Path 4, PathOneWay 5 (`signal_type.h:22-28`). The "one-way block" default of D20 is `Block` with a single side bit; there is no separate enum value.
- **(b) What `CmdBuildSingleSignal` accepts** (`rail_cmd.cpp:1070-1100`):
  - Tile must be `IsPlainRailTile` and have the track, else `STR_ERROR_THERE_IS_NO_RAILROAD_TRACK` ("there is no railway track"). A bridge head is not a plain rail tile, so signals on heads fail with this message.
  - `if (TracksOverlap(GetTrackBits(tile))) return STR_ERROR_NO_SUITABLE_RAILROAD_TRACK` ("no suitable railway track"). `TracksOverlap` (`track_func.h:540`) is false for 0 or 1 bits, and for exactly `Upper|Lower` or exactly `Left|Right`. Any other multi-bit tile (X+Y crossing, a switch/junction of three, a corner pair) refuses signals.
  - So: a signal is allowed on a single X, Y, Upper, Lower, Left or Right piece. Two parallel 45° pieces on one tile (Upper+Lower, or Left+Right) allow a signal on each. Two crossing or joining pieces do not. Signals must therefore sit on tiles with one piece, or the parallel pair.
  - Slopes/ownership: `CheckTileOwnership` only. No check for a bridge above: a tile under a bridge span is still a plain rail tile, so a signal there is allowed (inferred from the absence of any `IsBridgeAbove` test in the function).
  - Also refused: `sigtype >= End`, `sigvar >= End` (`:1072`, `CMD_ERROR`); `signals_copy` not overlapping `SignalOnTrack(track)` (`:1082`, `CMD_ERROR`).
  - Rail must exist first, and tracks added later onto a tile with signals that make an overlap fail with `STR_ERROR_MUST_REMOVE_SIGNALS_FIRST` (`:451`). Build order (all rail, then bridges, then signals) already avoids that.
- **(c) Cost by type.** None. New signal: `_price[Price::BuildSignals]` (`:1096-1099`). Changing type on an existing signal is free; changing variant costs build + clear.
- **(d) Estimate.** `GameJunctionPricing::SignalCost()` returns `_price[Price::BuildSignals]` (`junction_game.cpp:150-153`); `EstimateJunction` adds it once per `JunctionSignalStep` on a valid tile (`junction_layout.cpp`, signal branch). It assumes one flat price per signal, which matches (c). It does not check whether the signal would be legal (see 1b), so a generated layout with a signal on an overlapping tile would price fine and fail at build time.

## 2. Bridges (`CmdBuildBridge`, `tunnelbridge_cmd.cpp:308`)

- **Span tiles** go through `CheckBuildAbove` (`:288`). For a `Railway` tile the handler is `CheckBuildAbove_Rail` (`rail_cmd.cpp:3231`): any `IsPlainRail` tile passes at zero cost. So (a) diagonal/half-tile track, (b) multi-bit tiles including switches and crossings, and (c) signals under the span are all allowed. Non-plain rail (depot, waypoint) needs height clearance. Tile types with no handler are cleared (LandscapeClear, so clutter under the span is paid for once).
- **Height rules for span tiles** (`:497-516`): `GetTileMaxZ(tile) > z_start` gives `STR_ERROR_BRIDGE_TOO_LOW_FOR_TERRAIN` ("bridge is too low for the terrain"); `z_start >= tileZ + max_bridge_height` gives `..._TOO_HIGH_FOR_TERRAIN`; an existing bridge above gives `STR_ERROR_MUST_DEMOLISH_BRIDGE_FIRST`. On flat ground the deck is one level above the heads and flat span tiles pass (no clearance rule beyond this). Default `max_bridge_height` is 12 (`world_settings.ini:496-499`).
- **Head tiles** (`:380-420`): both are cleared with `LandscapeClear` before the ramp is made. A head tile that already holds track is therefore cleared and replaced (a plain rail tile clears if no train/foreign owner). Heads must be same height (`STR_ERROR_BRIDGEHEADS_NOT_SAME_HEIGHT`), same row or column (`STR_ERROR_START_AND_END_MUST_BE_IN`), not equal, and not on x==0 or y==0 (`STR_ERROR_TOO_CLOSE_TO_EDGE_OF_MAP`). Ramp slope handled by `CheckBridgeSlope`; flat heads cost nothing. A head carries one straight piece along the bridge axis implicitly (`MakeRailBridgeRamp`), so a layout must not list `JunctionTrack` on a head tile; the existing `MakeTestJunctionLayout` follows that (`{4,0}`/`{4,4}` heads, no track listed there). Any track the layout leads to the head must come from the neighbouring outside tile pointing along the axis.
- **Length.** `CheckBridgeAvailability(type, len)` (`:236`) with `len` = middle tiles (`GetTunnelBridgeLength`, the same value `CmdBuildBridge` uses before adding 2): needs `min_length <= len <= min(spec max, construction.max_bridge_length)`, default setting 64 (`world_settings.ini:483-490`), and `avail_year`. `STR_ERROR_BRIDGE_TOO_LONG` on overflow. With QueryCost flag it checks only the setting maximum (`:238-241`). Vanilla `_orig_bridge` (`table/bridge_land.h:774-`, columns min/max middle tiles, speed): wooden 0/unlimited/32, iron-suspension-like 0/2/48, 1930 types 0/5/64, 2-10/80, 3/unlimited/96 and 112, 3/7-9/160-240, 0/2/256, then 1995-2010 types min 2/unlimited/320-608. So a 1-2 tile span only has the slow types; fast rail types need spans of 2-3+ tiles (units of `spec->speed` vs `max_speed` not compared here).
- **`ChooseJunctionBridgeType(railtype, length)`** (`junction_game.cpp:43-88`):
  - Speed-limited rail type: cheapest type with `spec->speed >= rail_speed` among those passing `CheckBridgeAvailability(type, length)`; returns `nullopt` if none.
  - Unlimited rail type (`max_speed == 0`): target = fastest buildable train engine compatible with the rail type (D45); cheapest type at least that fast, else fastest, else cheapest.
  - It depends on the span length only, so the generator can only influence the type through the length; a span too short for fast types (min_length) or too long for some types can leave `nullopt`, which makes `Post` return false (`:177`) and `PriceBridge` give `STR_ERROR_CAN_T_BUILD_BRIDGE_HERE`.
- Bridges cannot cross bridges ("must demolish first") and a new bridge over another bridge's head is refused, so two bridges in a layout must not overlap in span or share head tiles on the same axis (`:487-490`).

## 3. Pure geometry for route tracing

All are inline functions over small tables, no map access. The tables are `extern const` arrays defined in `table/track_data.h` (and `_tileoffs_by_diagdir` for the offset one), in the main library, so they link into the test binary (inferred; confirmed indirectly: `junction_layout.cpp:76` uses `TrackExitdirToTrackdir`/`TrackdirToExitdir` in code that `tests/junction_layout.cpp` already exercises, and that test includes `track_func.h` and `map_func.h`).

- **Exit diagdir of a trackdir:** `TrackdirToExitdir(Trackdir)` (`track_func.h:343`). Asserts `IsValidTrackdirForRoadVehicle`, so not for RvRev.
- **Tile step as x/y delta (no TileIndex):** `TileIndexDiffCByDiagDir(DiagDirection)` (`map_func.h:487`) returns a `TileIndexDiffC`. The rail-only table `_trackdelta` is `static` in `rail_cmd.cpp:806`, not usable; derive the delta from the exit diagdir instead. Avoid `TileOffsByDiagDir` (`:574`), which depends on map width.
- **Trackdirs enterable from a diagdir:** `DiagdirReachesTrackdirs(DiagDirection)` (`:450`; entering moving in that direction). `TrackdirReachesTrackdirs(Trackdir)` (`:479`) is the same keyed by the exit of a trackdir, and is the successor set: it returns 3 trackdirs (straight on, plus the two 45° turns, e.g. NE gives `X_NE, Lower_E, Left_N`; `table/track_data.h:14-20`). 90° turns are not in it.
- **Reverse:** `ReverseTrackdir` (`:220`), `TrackToOppositeTrack` (`:204`), `ReverseDiagDir` (`direction_func.h:128`).
- **Axis vs half-tile piece:** `IsDiagonalTrack`/`IsDiagonalTrackdir` (`:514`, `:526`) = X/Y only (see vocabulary trap).
- **45° turn between consecutive trackdirs:** no direct helper (not found). Derive: `next` is a 45° turn from `cur` iff `next` is in `TrackdirReachesTrackdirs(cur)` and `IsDiagonalTrackdir(next) != IsDiagonalTrackdir(cur)` (axis piece to half piece or back, inferred from the table). A run of same-handed 45° turns is Lower/Upper alternation (`_next_trackdir`, `table/track_data.h:22`). Left vs right turn sign needs a small table in the generator (inferred).
- Also: `TrackExitdirToTrackdir(Track, DiagDirection)` (`:365`), `TrackEnterdirToTrackdir` (`:390`), `TrackdirToTrack`, `TrackToTrackdir`, `NextTrackdir` (`:307`, the trackdir to use on the next tile), `SignalAlongTrackdir` (`signal_func.h:24`).
- Direction helpers in `direction_func.h`: `DiagDirDifference` (`:141`), `ChangeDiagDir` (`:159`), `DiagDirToAxis` (`:224`). There is no `Trackdir` to `Direction` function (not found).
- Existing test precedent: `tests/junction_layout.cpp` includes `track_func.h` and `map_func.h`; it is the only test file including `track_func.h`.

## 4. Build steps

- **Per bit, one command.** `MakeJunctionBuildSteps` loops `for (Track t : jt.tracks)` and pushes one `JunctionRailStep` per set bit (`junction_layout.cpp`, the first loop); each step posts `CmdBuildSingleRail(tile, railtype, track, auto_remove_signals=false)` (`junction_game.cpp:173`). Then one step per bridge, then one per signal.
- **Run commands exist.**
  - `CmdBuildRailroadTrack(flags, end_tile, start_tile, railtype, track, auto_remove_signals, fail_on_obstacle)` (`rail_cmd.cpp:942`). Drags in a line with `ValidateAutoDrag` (`:825-868`): for X/Y it builds along the axis; for Upper/Lower/Left/Right it builds a 45° staircase, toggling the half-piece each tile (`:926-935`) and requires start/end on one such diagonal line. No explicit length limit beyond `Map::Size()`. With `fail_on_obstacle=false` it silently stops at the first obstacle after a success. Each tile is still a full `CmdBuildSingleRail`, so cost and validity equal the per-tile path.
  - `CmdBuildSignalTrack(flags, tile, end_tile, track, sigtype, sigvar, mode, autofill, minimise_gaps, signal_density)` (`rail_cmd.cpp:1468`). `signal_density` must be 1..20 tiles (`:1285`), a signal is forced on the first tile, spacing is fixed or minimised-gap; direction is copied from an existing signal on the first piece, otherwise two-way (one-way only for PBS types, `:1311-1316`). It cannot place a signal at arbitrary offsets or in per-signal directions, so it fits a uniform leg, not an irregular layout (inferred).
- **Ticks per step.** `BuildJunctionWindow::OnRealtimeTick` (`junction_gui.cpp:411-414`) calls `seq.Tick(poster)` once per realtime tick; `Tick` posts one step and waits for the command callback (`junction_build.cpp:32-41`, `CcJunctionStep`). In single player the command goes into `_local_execution_queue` and runs on the next game tick (`network/network_command.cpp:263`, `:321`), so one step per game tick, about 30 ms at normal speed (inferred; paused-game behaviour not checked).
- **Estimate for ~400 bits + ~60 signals + a few bridges:** about 400 + 60 + ~4 = ~465 steps, roughly 14 s at one step per 30 ms (inferred). Batching straight runs into `CmdBuildRailroadTrack` could cut the rail part to the number of runs (perhaps 40-80), but then `JunctionRailStep` and the estimate/ghost-progress code would need a run step. Not needed for correctness.

## 6. Layout capacity (`junction_layout.h`)

- Several track bits on one tile: yes (`JunctionTrack::tracks` is `TrackBits`; the build loop splits per bit). Two entries with the same offset also work (not checked for dedupe).
- Signals on any trackdir: yes (`facing` is a `Trackdir`); type and variant per signal, so pre-signals and path signals are expressible. Layout-side legality (single piece or parallel pair per tile, not on a head) is not checked anywhere.
- Several bridges: yes (`std::vector<JunctionBridge>`), straight row/column only; the estimate computes span tiles from start/end.
- Bridge over track: yes, tested (`MakeTestJunctionLayout`); estimate counts clearing once.
- Missing: a "reserved empty" tile marker; route/movement metadata; prio-piece or leg-end metadata; per-bridge type or height; any record of why a tile is in the layout. Footprint (`size`) is a bounding box only; tiles inside it with no entry are not claimed by `EstimateJunction` (it only checks occupied tiles).

## Gaps / surprises

- `EstimateJunction` validates nothing about signal legality, bridge-head overlap or a track listed on a bridge head; the generator and its rule checker must enforce these (checks in 1b, 2). A head tile with listed track is silently cleared by the bridge command after being priced as track.
- Signal legality is tile-local and cheap to test in pure code: `TracksOverlap` is pure in `track_func.h:540`; add it as a rule (single piece or Upper+Lower or Left+Right).
- Pre-signals and `PathOneWay` need no pipeline change; only the generator and the window's type choice are new. Block default must come from a new setting, not `default_signal_type`.
- The word "diagonal" is inverted relative to OpenTTD's `IsDiagonalTrack` (see top).
- No string client setting precedent in `gui_settings.ini`; the `SDTC_SSTR` template must be added there.
- Bridge type choice has no knob for the generator except span length; very short spans can lose fast bridge types (`min_length`), and any layout with a span no type can cover fails at build time, not at estimate time (estimate does fail via `PriceBridge`, so it shows as a bad tile, which is acceptable).
- Bridges are one `JunctionBridgeStep` each, but the sequencer does one command per game tick, so ~470 steps is on the order of 15 s of building (inferred).
- A 400-bit layout with 64x64 limit (D62) is far beyond what hover pricing (D63, one `TestRail` per bit) will tolerate if not cached; the cache key in D63 matters.
