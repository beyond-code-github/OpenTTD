## 1. The order stage
- OrderJunctionTrackGraph (src/junction_topology.cpp:478). Band crossings (:521-:535): each non-row-edge crossing goes to ONE band, the outermost (southmost) band both edges span (`level = south - south % 2`).
- Sweep (:562-:614): items start as the S-side slots' first edges. Per even level, loop: (a) swap the first pending crossing whose two edges are both items and adjacent; else (b) expand the LEFTMOST item whose north end is a node at this level into that node's other edges (children sorted by far-slot distance). `pending` is local to the band; anything left at the band's end is the error (:614).
- Two things make a crossing unrealisable, both properties of the loop, not of the graph:
  1. Expansion order. Depth-first leftmost expands a tree edge before its crossing partner exists as an item. The crossings are on bundles (an edge crossing a whole tree edge before it splits), so the bundle must still be unexpanded when the partner appears.
  2. One band only. A crossing blocked in its outermost band by an in-between edge that crosses neither partner is never retried further north.

## 2. A general rule (measured)
- Rule A (expansion): expand an item only when no pending crossing names it with a partner that has not yet appeared as an item (`waits`); fall back to leftmost when every candidate waits. Swaps stay first. This is the design's own §8 text ("expand ... then apply the band's crossings as swaps") made true for tree edges: crossers go over the whole unexpanded bundle.
- Rule B (retry north): leftover band crossings carry to the next even level (both edges still span it) and fail only after band 0 (the realised-crossings check still applies later).
- Result: any: all 5 left crossings of band 8 swept (A alone). Keep: A leaves only (7,13), blocked at band 8 by e16 (N5->N8, path 10), which crosses neither e13 nor e7; B realises it at band 4 (north of row 2, after e7 has crossed row 2). Both pass OrderJunctionTrackGraph. T, LL_RR x L_R unchanged: `[topology]` 70 cases pass (one transient FAILED at src/tests/junction_topology.cpp:3150 on the first jt run did not reproduce in 2 reruns, INFERRED flaky or a build race), `[topologysweep]` passes (36.8 s Debug).
- Pure order-stage change (no structure/programs change) for these two; no engineer ruling needed: it realises the crossings the graph already commits to (D182, D203 one crossing set per bridge) with no new geometry choice. The block-move and different-key alternatives were not needed. Not measured: whether Rule A can deadlock (a cycle of waits) on other topologies; the fallback keeps it from hanging but then the old failure shows. Rule B is a choice (a later band widens the crossed lane bundle); design §8 chose the outermost band for room, so B as fallback only is the consistent reading.

## 3. Per direction: the placement contradiction
- Graph: rows 2 and 3 carry the E->W through legs e14 (N5->N6, path 8) and e15 (N4->N7, path 9). N3 (S5's split, far group E) is at level 4, north of row 2, so e3 (S5 trunk, paths 6,7) climbs through rows 3 and 2 and crosses both. - Reason chain (full, from the error, repeats removed): hug crossers (e14,row 2) <- lane split run (e14, node 5, row 2) <- hug crossers (e15,row 3) <- lane split run (e15, node 4, row 3) <- chain run e10 <- chain run e2 <- S port spacing <- chain run e3 <- bridge heads e3 <- hug crossers (e14,row 2). A cycle of difference constraints (src/junction_topology.cpp:2396 lane split run, :2418 hug, :2313 S port spacing, :2498 bridge heads, :2524 chain run).
- Geometry (INFERRED from the code and graph, not drawn): the crossers' columns are pinned by the S ports (4 adjacent ports = 4 columns, "S port spacing") plus each crosser's own curves (e10 turns into row 2 at N6, e16 leaves N5 for S7). A doubled bridge's heads must hug its outermost crosser tiles AND stand a floor beyond the lane split node (lane split run) AND stagger with the copy (D118). Row 3 needs heads outside 5 crossers' columns, row 2 outside 3; the heads of row 2 fall on columns row 3's crossers occupy and vice versa; the E split nodes N4, N5 sit east of both. No x assignment exists.
- Missing relation: nothing bounds how many crossers one doubled bridge may hug in that few columns. D209's cap (about 2 crossers / 4 middle tiles) exists in the cut (CutJunctionTrackBridges tries splitting into series bridges, that is why `series bridge heads` is absent from the chain) but 5 crossers across 4 port columns cannot be spaced out by series bridges either, because the crossers themselves are not spreadable: the S-port spacing (D142 adjacent lanes) pins them. What is missing is a relation that lets the crossers move apart (S-bends on the S trunks, D203) or lets the bridge be one long span or a tunnel (D190) for a crossing set this dense. Engineer question below.

## Decision card OC1-D1 (for the engineer)
Context: LL_RR x LL_RR keep-lane and per-direction produce dense crossing sets on the E->W through lanes (5 crossers in 4 columns on a doubled lane); keep also has main x main and joiner x joiner crossings. Options: (A) main x main: the lane that stays straight (through) goes over, the turning leg under; joiner x joiner: the one farther from the main line goes over. Consequence: simple, one rule for all; may force tunnels later. (B) Cost search over crossing assignment (D189 "situational"). Consequence: right in the long run, large change now. (C) For dense sets let the S trunks S-bend apart (D203). Consequence: needed for the placement contradiction; touches placement and the render. Recommendation: A for structure, C for placement, B later.
